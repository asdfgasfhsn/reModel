# MB86234 (the Model 2A TGP): instruction set and interpreter

The Model 2A's geometry processor is a Fujitsu MB86234 (the "TGP" of the
original Model 2 and 2A boards; the 2C's is an MB86235, `mb86235.md`). No
public manual for it has been found, and nothing here is taken from any
emulator: it is read from the program images the games upload
(`srallyc`'s, then `vf2`'s) and pinned by **running** their routines and
checking the mathematics they compute and what their callers expect. `crates/mb86234` implements it
(an interpreter and a disassembler), and since milestone 3 the 2A board
runs the uploaded program on it (`model2::tgp2a`; `model2a.md`).

Every statement says how it is known:

- **confirmed**: running the program under this reading gives the right
  mathematics for random arguments (`make tgp-check`), or two independent
  paths of the program agree, or the program's own code depends on it in
  a way nothing else would satisfy;
- **hypothesis**: fits everything seen, but nothing pins it (typically:
  only uncalled code uses it, or two readings give the same results);
- **unknown**.

Sources: the 1,665-word program `srallyc` uploads (`out/srallyc/tgp.bin`,
written by `make run GAME=srallyc`; it is also in the game's program ROM
at `0x5AE94`), and the 3,802-word one `vf2` uploads (`out/vf2/tgp.bin`),
which uses much more of the instruction set: its dispatch, indexed
addressing, program-memory tables, a second loop counter and the
arctangent (§ "What `vf2`'s program added").

## How the encodings were pinned

1. **Structure** (milestone 2): the dispatch table, the main loop, the
   moves' fields, the float immediates, calls and returns.
2. **The library** at functions `8`-`0x17`: two-word and one-word float
   functions the game never calls, each a few words long: add, subtract,
   multiply, divide, abs, negate, square root, int/float conversions,
   sine, cosine, tangent. Each unknown ALU code or operand form they use
   had a short list of candidate meanings; the one kept is the one under
   which the function returns the mathematics (sine within 5e-6 over
   ±100, the square root to 1 ulp, the others exact or to 1 ulp) for
   random arguments. The sine is the richest: a range reduction (abs,
   multiply by 1/pi, float to integer and back, subtract), a degree-12
   cosine polynomial from a coefficient table the start-up code builds
   (1/2, 1/24, 1/720, ... all positive, so the alternating signs pin which
   codes add and which subtract), a conditional load on the sign, and an
   integer parity test that negates the result.
3. **Consistency**: the rotations exist twice, with the polynomial sine
   (`0x29`-`0x2B`) and with the ROM's sine table (`0x32`-`0x34`); they
   agree to 1.5e-7. Function `0x5D` (the game's commonest) is `0x20`,
   `0x5E`, `0x05`, `0x21` called in a row; its output equals theirs bit for
   bit. The matrix stack round-trips through nine pushes and pops.
4. **The game**: a 4,832-frame coin-start run executes 101 million TGP
   words with no word of an unknown form, no empty read and no stuck
   call; the matrices the TGP writes into the display list are rotations
   (rows of length 1) with plausible translations, placed exactly where
   the list leaves room for them (`model2a.md` §7). When function `2`
   reports the start-up value of its error counter (`0x6000`, see below),
   the game calls function `1` (clear errors) once and never again.
5. **The race** (milestone 5): the course search (functions `0x52`,
   `0x53`) reads the TGP's data ROM, whose layout (a cell's polygon count
   and the byte offsets of its polygons and attribute words) fixes how
   often its loop must run; the `loop` word below was read from that.
   With it the car drives: it accelerates, steers, hits the barriers and
   bounces off, and while airborne falls at 10 m/s² (in the course's
   units, the wheel track being 1.8 and the wheelbase 2.75 of them: metres)
   (`model2a.md` §9).

`make tgp-check` (`remodel tgp-check`) reruns steps 2 and 3: every
function the game calls, and the library, with random arguments, against
f64 maths and against the milestone-2 function model.

## Program layout

- **Fixed 32-bit words** (*confirmed*), uploaded one store per word.
- **Six vectors** at 0-5 (`BF60xxxx` jumps): word 0 (reset) to `0x10`, the
  others to two short interrupt handlers ending in `BF6E0000`
  (*hypothesis*: return from interrupt; interrupts aren't modelled and
  nothing seen needs them). The same six words begin the programs of
  `daytona`, `vcop`, `desert`, `manxtt`, `motoraid`, `dynamcop` and `vf2`.
- **Start-up (`0x10`-`0x6F`)**: constants in RAM0 `0..0xF` (0, 1, -1, 0,
  1.0, -1.0, pi, the matrix stack's base `0x130`, its depth, the depth
  limit 7, ...), pi/2 and 1/pi, copies of the first six in RAM1, the
  cosine coefficients at RAM1 `0x20` and a square root's seed line at
  RAM1 `0x3A`, the display-list cursor (`0x6000`, below).
- **Load check (`0x70`-`0x75`)**: each word read is answered with 8 until
  one arrives whose exponent field is 8 (a write to command port 8, below).
- **Main loop (`0x77`-`0xA0`)**: reads a command word, checks that its three
  copies of the function number agree (`F << 23 | F << 8 | F`, read
  through the exponent and mantissa views of `R13`), calls the word at
  `0xAF + F`, adds 1 to the command counter (RAM0 `0x65`). A bad word goes
  to an error routine that counts it (RAM0 `0x7C`), sets bit 1 of the
  flag word and records it in shared RAM near the top (`0x7F80`-`0x7FFF`).
- **Dispatch table at `0xAF`-`0x12E`**: 128 slots, function F at
  `0xAF + F` (*confirmed*); 48 point at a return.

## The machine model

| Part | What | How known |
|---|---|---|
| RAM0 | data RAM; direct addresses `0x00-0x7F`, indirect `0x000-0x1FF` (the matrix stack is at `0x130`) | confirmed (all of the program's state) |
| RAM1 | second data RAM; direct through the `op1` field, indirect at `0x200-0x3FF` of the same address space | confirmed: the coefficients stored through `0x220` are read as RAM1 `0x20` |
| registers | 64 numbers in the transfer fields, below | |
| input FIFO | register `0x21`: reading it takes the host's next word; a word that reads it waits while it is empty | confirmed |
| output FIFO | register `0x22`: writing it gives the host a word | confirmed |
| external bus | 24-bit addresses (the address registers hold 24 bits): the board's shared RAM after `63400000` (word addresses below `0x8000`, the rest of the low 16 bits mirrored), the function unit after `63000000` (ports `0x20`-`0x2B`), and **in both modes the data ROM from `0x800000`** (`Role::TgpData`: srallyc's `.29/.28`, 32-bit words; `model2a.md` §9) | the ROM and the width confirmed by the course search working (the race's ground contact; before, only 16 bits and no ROM were modelled, and function 7 read 0); the switch is a hypothesis (every shared-RAM access in the program is bracketed by these words) |
| program memory | readable as data: type `1E` with op1 bit 6, and group 5 transfers (`vf2`'s tables of jump targets, matrix slots, radii, an epsilon) | confirmed (`vf2`) |
| stack | return addresses of `BF64`/`BF66` and conditional calls | confirmed (calls nest three deep) |
| repeat | `3C04 n` runs the next word n times | confirmed (12-word matrix moves) |

**Timing** (*confirmed*): one word per step, no delay slots. A word's ALU
operation and its transfer both read their operands at the start of the
word and write at the end, so an ALU operation sees what the *previous*
word moved. One special case: when the ALU operation and the transfer of
the same word both write the accumulator, a transfer reading it next sees
the ALU's result and the next ALU operation the transferred value (the
square root's Newton step and the command check depend on this; any
other order gives wrong roots).

**`BF00`, the loop** (*confirmed*). It is the course search's only use
(word `0x639`, closing the loop that tests one polygon a pass), and LC
(`0x0C`) is written only at the search's start, with the first word of the
cell (`lc = ext[ar3]+1`). Milestone 4 read it as "jump if the zero flag is
clear", which made the car stand on the start line but run away once it
moved. The evidence for the counter:

- Every cell of the course data has its polygons (16 words each) and then
  its attribute words (one each) laid out back to back, and the cell's
  first word times 16 is exactly the distance between the two: the first
  word is the polygon count. Read as a jump on the flags, the loop ran on
  past the count (16 passes in a cell of 6 polygons under the car on the
  start line, 47 in another), into the next cells' polygons, and took
  whichever one first contained the wheel in plan view, so the ground the
  game got was another place's; since the add before it counts a ROM
  pointer that is never 0, the loop could only end by finding something,
  and the second and third cells the caller offers were never searched.
- Counting LC down, the search runs a cell's polygons and stops; the loop
  word must leave the flags alone, since after the last pass the caller
  takes the zero flag (still the add's: clear) as "not found" and tries
  the next cell.
- The race drives (`model2a.md` §9), and `make tgp-check` searches a
  made-up course whose cells are each followed by a polygon covering the
  whole course: the program finds the right polygon in the right cell
  every time, and under the old reading finds the decoy.

Conditions (the byte after `BE`): `00` jumps when the last result was
zero (*confirmed*: the command check, the parity test, the square root of
0), `10` when it was not negative (*confirmed*: the stack depth limit),
`20` when it was negative or zero (*hypothesis*: the pop's depth-0 test
and `vf2`'s clamps to [-1, 1] use it, where "negative" alone also fits),
`A0` when the function unit's arctangent has |x| < |y| (*confirmed* by
`vf2`: it then divides x by y instead of y by x, so that the ratio it
writes is at most 1). ALU operations set the flags from their result; the
multiply-only code 8 doesn't.

### Operands

`op1` is 7 bits, `c9` 9 bits. `c9` below `0x80` is a direct address; with
bit 7 (`0x80`-`0xFF`) it is **relative**: the pointer register plus its
base plus `c9 & 0x7F`; with bit 8 (`0x100`) it is **indirect**: the pointer
register, which then steps by the signed 5-bit step in bits 0-4. In an
indirect operand bit 5 set means the pointer alone, bit 5 clear
**indexed**: the pointer plus its base, and bit 6 with bit 5 clear
**circular** (below). The pointer is AR3 for the
single-address types (`1C`-`1E`) and for `op1`; AR2 for `c9` of the other
types and of `1E` with op1 bit 6. The bases are AR0 for AR2 and AR1 for
AR3. Internally an address is 10 bits (RAM0 below `0x200`, RAM1 above)
unless the type fixes the RAM (below); externally 24 bits.

How known (*confirmed* unless said): `vf2` walks an object list in shared
RAM by setting AR0 to an object's address and AR2 to 0, 12, ... (the
pointer advances by exactly the object's size, 37 words, after); it keeps
bitmask tables at RAM0 `0x40` and `0x80` and indexes them with AR1 = `0x40`
or `0x80` and AR3 = 0-63 (the tables are cleared just before; without the
base it would write over its constants at 0-63); it keeps 30-entry tables
in shared RAM at `0x3E20` + index the same way; it reads tables in program
memory as AR0 = table, AR2 = index. Relative operands use the base too:
`vf2` zeroes AR0 and AR1 before 3x3 products that use them. `srallyc`
sets AR0 = 0 and AR1 = `0x200` at start-up and never again: the latter is
why its matrix stack, which it addresses as `[AR1 + AR3]` with AR3 =
`0x130`.., is in RAM1 (below). Bit 5 was "no difference seen" while both
bases were constant.

**Circular operands** (*confirmed* by `vf2`; the ring's length is a
hypothesis). Every indirect `c9` in both programs has bit 7 set, so bits
5-7 are a mode: `100` indexed, `101` the pointer alone, and `110`,
which only `vf2`'s functions `0x6C`-`0x6F` use (`1C1`): indexed, with
the pointer's step wrapping round a ring of 64 words (it counts
`0x3E, 0x3F, 0, 1, ...`). Those functions read rotation angles and
translations, one after another, from shared RAM `0x3800` + a pointer
kept in RAM0 `0x3D`, which the program sets to 0 at start-up and nothing
else resets. The i960 writes them into a ring of exactly 64 words there
(buffer RAM `0x90E000`-`0x90E0FF`, the next write after `0x90E0FC` going
to `0x90E000`), continuing round it from frame to frame; the two agree
on every frame of a coin-start run (the first slot the i960 writes in a
frame is the pointer at that frame's first call, 2,632 frames,
`vf2`'s player-select screen included). Without the
wrap the pointer ran on past the ring (to `0x1601` by frame 1,009 of a
coin-start run) and read whatever else was in shared RAM: denormals and
NaNs that went into the fighters' bone matrices, from which the game
works out where they stand; with it, they fight (`docs/games/vf2.md`).
Whether the 64 is fixed or set by a register (`0x0A` is set to 3 and
`0x3C` to 2 at start-up, either of which could encode it, and neither is
written again) is unknown, as
is how the ring is aligned: the model wraps the pointer's low six bits,
which is the same for this ring, whose pointer starts at 0. No other
operand in either program has this mode, so nothing else changes
(`srallyc`'s state hash is the same).

### Transfers and multiplier loads: the type field

The 5-bit type is a **group** (bits 2-4) and op1's **mode** (bits 0-1:
`00` direct, `01` relative to AR3 + AR1, `11` indirect through AR3).
A transfer moves c9's operand to op1's; a multiplier load (top bits
`000000`) loads R13 from op1's operand and R10 from c9's. The group gives
where each is:

| Group | Types | op1 | c9 | How known |
|---|---|---|---|---|
| 0 | `01`, `03` | external | internal | `03` hypothesis (`srallyc`'s error log); `01` confirmed (`vf2` multiplies an object's vertex, read from shared RAM relative to AR3, by a matrix) |
| 1 | `04`, `07` | external | internal | `04` confirmed (`vf2` writes RAM0 angles to the sine port, `ext[0x20] = [0x10]`, and multiplies the sine and cosine ports by RAM0 values); `07` confirmed (both games write the current matrix into the display list) |
| 2 | `08`, `09`, `0B` | internal | external | confirmed (`08`: table rotations; `0B`: `srallyc`'s polygon copy; `09`: `vf2` writes cosine, sine, cosine from the ports into a matrix relative to AR3) |
| 3 | `0C`, `0D`, `0F` | **RAM1** | **RAM0** | confirmed (below) |
| 4 | `10`, `11`, `13` | **RAM0** | **RAM1** | confirmed (below) |
| 5 | `14`, `17` | internal | program memory | confirmed (`vf2`: `17` copies its constants 0, 1, 1.0 from program words `0x1D3`.. to RAM0 0..; `14` reads radii from a table) |
| 7 | `1C`-`1F` | the single-address types, below | | |

**Groups 3 and 4 fix the RAM** of each operand, direct, relative or
indirect: in group 3 op1's is RAM1 and c9's RAM0, in group 4 the other way
round (*confirmed*). A multiplier load reads both operands in one word,
one from each RAM. The evidence: `vf2` copies values into RAM1 with a
group 3 transfer (`ram1[0x1A] = [0x06]`) and reads them back with a group
4 one at the same direct address (`[0x03] = [0x1A]`); its push copies the
current matrix with `13` (to RAM0 `0x20`) and `0F` (back to the next
slot), its matrix slots and the functions that store into them agree only
if the slots, written with `0F`, are RAM1 (`0x220` and `0x2E0` + 12 k,
which an uncalled function also walks as RAM1 `0x229`.. with base `0xC0`);
its vector arguments go to RAM0 `[0x03]`.. and a group 4 multiplier load
reads them as op1 against a matrix element as c9. In `srallyc` the same
rule puts the matrix stack in RAM1 `0x130`.. and explains the `+ 0x200`
its display-list write adds to the matrix's address for type `07`
(previously modelled as "type `07` sees RAM0 at `0x200`"); `srallyc`'s
distance function `0x50` reads its two points from the two RAMs
(`ram1[0x3D] - [0x3D]` became `[0x3D] - ram1[0x3D]`: the same distance).
`srallyc` runs bit for bit as before under this reading (state hash and
`make tgp-check`).

| Type | Transfer | How known |
|---|---|---|
| `1C` | [c9] = reg op1 (op1 bit 6 set: external[c9]) | confirmed |
| `1D` | reg op1 = [c9] (op1 always has bit 6 set) | confirmed |
| `1E` | reg op1 = external[c9]; with op1 bit 6: reg = **program memory**[c9 through AR2] | external confirmed; program memory confirmed (`vf2`: a jump target from a table at `0xD08` + an object's type, then `BF62` to it; matrix slot addresses from `0x2F6`; the arctangent's epsilon `prog[7]`) |

## The function unit (external bus, `63000000` side)

The board's `CoproData` ROM `opr-14742a.45`/`.46` (64K 32-bit words) holds,
*confirmed numerically*: a quarter-wave sine of 16,384 floats (65,536 steps
a turn, within 3e-8) at `0`; an arctangent table of 16-bit pairs (`-n`,
`n`; 8,192 is 45 degrees) at `0x4000`; pairs (slope, intercept) of linear
approximations to `1/m` on 8,192 segments of [1, 2) at `0x8000`, and to
`1/sqrt(m)` on 4,096 segments each for even and odd exponents (the odd
ones times sqrt 2) at `0xC000`. (`.58`/`.59` and `.62`/`.63` hold the
reciprocal and inverse square root again as 24-bit mantissas, one per
segment midpoint; this program doesn't need them.)

The ports, as the program uses them (*hypothesis* for the hardware's
exact arithmetic; *confirmed* that these results are what the program
needs: reciprocals and inverse square roots to 1 ulp, the table rotations
equal to the float ones):

| Port | Write | Read |
|---|---|---|
| `0x20` | an angle (low 16 bits) | its sine |
| `0x21` | | its cosine |
| `0x28` | a float x | the slope's magnitude for x's mantissa segment, times 2^-e |
| `0x29` | | the intercept, times 2^-e, with x's sign |
| `0x2A`, `0x2B` | a positive float | the same for 1/sqrt(x) |
| `0x24`, `0x25` | x, y (floats) | |
| `0x27` | the smaller over the larger (y/x, or x/y when \|x\| < \|y\|: condition `A0`), or 0 below an epsilon | atan2(y, x), 65,536 a turn, signed |

The program then computes `intercept - m * |slope|` with m = x with its
exponent set to `0x7F` (`5100007F`): one multiply and one subtract give
1/x or 1/sqrt(x) to full float precision.

**The arctangent** (*confirmed* as `vf2` uses it; how the port forms the
angle is this model's): the ROM's table at `0x4000` has 16,384 entries over
[0, 1] (entry i = atan(i / 16384) in 65,536ths of a turn, `0x5000`: 2,555 =
atan 0.25), the angle in the low 16 bits and its negation in the high.
The model looks up the ratio written to `0x27`, then places it in its
octant from the signs of x and y and which was larger. `vf2`'s function
`0x27` returns this for (x, y) and function `0x26` turns y into asin(y)
as atan2(y / sqrt(1 - y^2), 1), and the code at `0x3DF` an arccosine as 16,384 minus it: the
model gives 8,192 for (1, 1), 24,576 for (-1, 1), -8,192 for (1, -1) and
5,461 (30 degrees) for asin 0.5. Port `0x2C` is written once at start-up
(-1): *unknown*.

## RAM use (`srallyc`; the matrix stack is in RAM1, see the type field)

| RAM0 | Use |
|---|---|
| `0..0xF` | constants and the matrix stack variables: `[7]` the current matrix's address, `[8]` the stack base `0x130`, `[9]` the depth, `[0xA]` the depth limit 7 |
| `0x10`..`0x1B` | a matrix's temporary copy (push) |
| `0x28`..`0x33` | the 3x3 product's result (`0x24`) |
| `0x34`..`0x4F` | temporaries (cosine and sine in `0x34`, `0x36`) |
| `0x65` | the command counter |
| `0x70`..`0x7B` | the four vector registers (x at `0x70 + i`, y at `0x74 + i`, z at `0x78 + i`) |
| `0x7C` | the error counter (start-up leaves `0x6000` in it, the value in the accumulator then) |
| `0x7D` | the display-list cursor (`0x6000`, reset by function 3) |
| `0x7F` | the flag word (copied to ST) |
| RAM1 `0x130`.. | the matrix stack: 12 words (3x3 row by row, then the translation) per slot, 8 slots (addressed as `0x130` with AR1 = `0x200`) |

RAM1: `0..5` copies of the constants, `0x20`-`0x25` the cosine
coefficients, `0x3A`-`0x3C` the square root's seed line (0.590 + 0.417 m)
and 1/sqrt 2, `0x34`.. and `0x53`.. scratch.

## What `vf2`'s program added

`vf2`'s 3,802-word program (same six vectors) has its main loop at
`0x2C`-`0x3E`: it reads the command word into R13, moves it to LC (8
bits: F), checks R13's exponent field against it (a mismatch calls the
error routine at `0x1AF`, `FE04`), adds `0x3F` and jumps through ACC
(`BF624019`) into the table at `0x3F` + F of `BF60` jumps; every function
ends with a jump back to `0x35`. Its matrix stack is at RAM1 `0x1A0`
(function 0 sets the pointer in RAM0 `0x3F`), functions 1 and 2 push and
pop, 3 loads the identity, 5 reads the matrix, 6 translates, 7 scales,
`0x13`-`0x1A` are float add, subtract, multiply, divide, int to float,
float to int, 1/sqrt and sqrt, `0x21`/`0x22` sine and cosine, `0x24`/`0x25`
r sin a and r cos a, `0x26`/`0x27` asin and atan2, `0x29` transforms a
point, `0x2B`/`0x2D` distances, `0x30` normalises, `0x34` writes the
current matrix into the display list (byte offset in, then a 0 reply),
`0x36`/`0x37` load and store matrix slots (two banks of 16 in RAM1),
`0x6C`-`0x6E` rotate (as functions 8, 9 and `0xA` do) by an angle and
`0x6F` translates by a vector, each taken from the i960's 64-word ring in shared RAM (a circular
operand, above), `0x3A`/`0x3B`/`0x3E` a sphere collision test over shared-RAM tables
(`0x3E80`.., `0x3F40`.., `0x7E80`..), and `0x4A` walks an object list in
shared RAM by type (a table of handlers at `0xD08`), writing results back
into it. Each of those was run on the interpreter with chosen arguments
and gives the expected mathematics (a scratch harness; not yet a `make
tgp-check` for `vf2`). With them the game draws its fighters and stages
(`docs/games/vf2.md`).

## Not known

Control registers 0, 2 and 6 (the course search writes 4 to 0 when it
gives up on all three cells, and on its returns 1 to 6 or 2; nothing reads
them back), registers `0x0A` and `0x3C` (`4A`, `7C`), condition `0A` (only
in `vf2`'s error routine), port `0x2C`, `repeat 0` (`vf2` clears RAM with
it at 0, `0x200` and `0x300`, which suggests 256, and a RAM0 of 256
words; executed once here), whether ALU 12 multiplies, rounding and
special values (the interpreter uses IEEE single precision, round to
nearest, with denormals), interrupts, the clock and cycle counts, RAM
sizes (512 words each assumed), and the circular mode's ring: its
length (64 here) and alignment, and whether a register sets them.

## Tools

- `make tgp-disasm GAME=srallyc`: the image (default `out/GAME/tgp.bin`)
  listed with mnemonics, header, dispatch table and function entry points
  (`out/GAME/tgp.lst`); in `srallyc`'s and `vf2`'s programs only data
  words and `vf2`'s `BE0A` show as `??`. A circular operand shows as
  `[ar1+ar3]%+1`.
- `make tgp-check GAME=srallyc`: the functions on the interpreter with
  random arguments, against the maths and `model2::tgp2a_hle`.
- `make run GAME=srallyc`: the `tgp calls` table, `tgp-calls.txt`, and the
  chip's words run and any unknown words.

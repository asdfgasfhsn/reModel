# reModel status

The tracking table: what is done, what is in progress, and the game-by-game
history. The README has the short version; the findings are in [docs/games/](games/README.md) and [docs/hw/](hw/).

## Status

The original program runs on the reference interpreters from boot through
attract, coin-up, course and skater select into a race, with textured 3D
frames written as PNG snapshots. The interpreters run the bench (attract into
a race) at about 2x real time on a desktop CPU, with the geometrizer on its
own thread. The sound board (68000 + SCSP) and the DSB2 MPEG music board
render offline from the command bytes a run captures (`make sound`, `make
music`). There is no live window yet.

| Smooth motion (in-between frames for displays over 60 Hz, `model2::smooth`) | opt-in; played natively on a 120 Hz 3440x1440 display with `topskatr` (2026-11-08) and it plays smoothly, but untested in a browser on a fast display (the player's settings or `remodel-play --smooth`, the browser's `?smooth=1` or its panel; off by default, as it adds a game frame of latency): with the native geometrizer, the refreshes between two game frames rerun the newest frame's display list with each matrix interpolated between its values in the two frames (rotation on the arc, scale and position linearly), matched by model address, place and position; camera cuts aren't blended. Render-only: same state hashes with it on (`topskatr`, `sgt24h`, `vstriker`, `doa`). An in-between costs about 0.2-0.4 ms (2C) or 1.4-1.8 ms (2B) natively; `make smooth-frames` draws them to PNGs; see `docs/hw/geometrizer.md` ("Smooth motion") |
| Anti-aliasing and a depth buffer for the 3D layer (`gpu::Quality`) | opt-in, render-only (state hashes unchanged: `topskatr`, `srallyc`). MSAA 4x (8x natively where the GPU has it) resolved by coverage, so edges blend with tile skies and the backdrop; the software renderer supersamples snapshots (`--aa N`). The depth buffer (1/z per vertex, per window, with the game's order kept for skies, flat shadows, translucent layers, very deep floors and groups of layers sorted together) fixes crossing and mis-sorted polygons; compared frame by frame on all 18 games (`make depth-check`) with the differences mostly fixes: characters' limbs and clothes, crossing beams, billboards. Not yet on by default. Player menu and `--aa`, `--depth`; browser panel and `?aa=4&depth=1`; `docs/enhancements.md` has what was decided and `docs/gpu.md` the cost (about 1 and 2 ms at 1080p) |
| Run-ahead (the game shown frames ahead of itself, `model2::runahead`) | opt-in in the native player (a setting: off, 1, 2 or 3 frames; `remodel-play --run-ahead N`), not yet in the browser: after each game frame a second machine copies the game's state (only the memory either side wrote since the last copy, the chips directly, their decode caches kept: 0.8-1.7 ms) and runs N frames with the same inputs, and that is what's drawn. The game itself never runs them: coin-start runs of all sixteen games keep their state hashes, and every frame shown (where the inputs held) is the plain run's N frames later, picture, state hash and smooth motion's in-betweens alike (`make run-ahead-check`). Each frame ahead costs about a game frame more: interpreted, run-ahead 1 adds 6.7-8.4 ms a frame on 2C (its game frames 5.3-6.8 ms) and 7.8-15.7 ms on 2B (6.1-12.1 ms), run-ahead 2 11.6-14.3 and 14.1-23.2 ms; the wait and copy in that are 0.9-2.3 ms, where a whole save and load would take 5-9 ms. Each game's own input lag, measured (`make input-lag`): most show a control in the first frame that reads it, so there's nothing to hide; `stcc`, `indy500`, `doa`, `fvipers`, `dynabb97` one frame, `bel` three, `sgt24h` four. *Unconfirmed:* not yet played with by hand; see `docs/play.md` ("Run-ahead") |
